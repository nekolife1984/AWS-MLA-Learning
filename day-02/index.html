ファイル形式の選び方

ML のデータはまず「どこに・どの形式で置くか」が勝負。CSV / JSON / Parquet / ORC / RecordIO — 形式を間違えると、学習の速度もコストも大きく変わります。

# データレイク# オブジェクトストレージ# 列指向# Parquet
💡

一言で言うと

Amazon S3 は、ML のデータレイクの中心になるオブジェクトストレージで、形式を間違えると学習コストも速度も大きく変わる。

01

データレイク ― すべてのデータは S3 に集まる

生データから加工済みデータまでを S3 にまとめて置くのがデータレイク。SageMaker も Glue も Athena も、みんな S3 から読み書きします。

ためるデータ

📥 生データ RAW

ログ、画像、センサー値など、手を加えていない元のデータ。

✨ 加工済みデータ PROCESSED

クレンジングや変換を終え、分析・学習にすぐ使えるデータ。

›
🪣

Amazon S3 DATA LAKE

バケット ＋ キー（プレフィックス）で管理する、データレイクの中心地。

›
読み書きするサービス

🔎 Athena QUERY

S3 上のデータに SQL でクエリする。

🧰 Glue ETL / CATALOG

データの変換とカタログ管理を担当。

🤖 SageMaker TRAIN

S3 のデータを読み込んでモデルを学習。

PREFIX の切り方（例）

s3://ml-lake/raw/logs/2026/10/28/access-001.parquet s3://ml-lake/processed/training/category=sales/data.parquet

日付やカテゴリでプレフィックスを分けておくと、必要な範囲だけを絞り込んで読めるので、検索も集計も速くなります。

置く

Amazon S3ストレージ担当

データを安く・大量にためる場所そのもの。クエリや変換の機能は持ちません。

探す・聞く

Athena / Glue Data Catalogクエリ＆カタログ担当

Athena が SQL クエリを、Glue Data Catalog が「どのデータがどこにあるか」の目録を担当します。

変える

AWS Glue変換（ETL）担当

CSV を Parquet に変換する、形式を整える、といった加工処理は Glue の仕事です。

02

行指向 vs 列指向 ― なぜ Parquet が速くて安いのか

Athena の料金は「読んだデータ量」で決まります。だから「必要な列だけ読めるか」が、そのまま速度とコストの差になります。切り替えて比べてみてください。

03

ファイル形式 5つを比べる

それぞれ「得意なこと」と「弱点」がはっきり分かれています。試験では用途から形式を選ばせる問題が定番です。

CSVComma-Separated Values

行指向テキスト

強み：人が見やすくて手軽。Excel でも開けるし、とりあえず置くには一番簡単。

弱み：圧縮と型情報が弱い。全部テキストなので容量がかさみ、列を絞って読むこともできません。

JSONJavaScript Object Notation

行指向半構造化

強み：半構造化データ向きで柔軟。項目が増減するログや API のデータを受け止めやすい。

弱み：キー名を毎行繰り返すため容量が大きくなりがち。大量データの繰り返し集計には不向きです。

ParquetApache Parquet

列指向★ 分析・学習の定番

強み：列指向で圧縮に強く、必要な列だけ読める。型情報（スキーマ）も保持します。

使いどころ：Athena や SageMaker での分析・学習の定番形式。迷ったらまず Parquet を思い浮かべてください。

ORCOptimized Row Columnar

列指向Hive 系

強み：Parquet に似た列指向形式で、圧縮と読み取りの速さに優れます。

使いどころ：Hive 系のエコシステムでよく使われる形式。Athena でも読み取りに対応しています。

RecordIORecordIO-Protobuf

バイナリSageMaker 専用寄り

強み：SageMaker 向けの Protobuf 形式。Pipe モードでデータをストリーミングしながら高速に学習できます。

使いどころ：大規模データの学習を効率化したいとき。分析用途ではなく「学習専用」と捉えるのがポイントです。

形式向き圧縮・型情報主な使いどころ
CSV 行指向 ✕ 弱い（型情報なし） 手軽な入出力・人が確認する用途
JSON 行指向 △ 柔軟だが容量が大きい 半構造化データ・ログの受け皿
Parquet 列指向 ◎ 圧縮に強く型情報あり Athena / Spark / SageMaker の定番
ORC 列指向 ◎ 圧縮に強く型情報あり Hive 系エコシステム
RecordIO ―（Protobuf） ○ 学習向けに最適化 SageMaker の Pipe モード学習
04

試験で問われるポイント

シナリオの「やりたいこと」から、置き場所と形式を即答できるようにしましょう。

1

大量データを安くためて分析したい → S3 データレイク

「大量の構造化・半構造化データを安くためて、Athena や SageMaker で分析したい」という要件が出たら、答えは S3 を中心にしたデータレイク構成です。

2

Athena で読むなら、列指向の Parquet / ORC

行指向の CSV / JSON より、列指向の Parquet / ORC の方が速くて安い。理由は「読む列だけ読めるから」。Athena は読んだデータ量で課金されるので、ここが直結します。

3

RecordIO ＋ Pipe モード = 高速な大規模学習

SageMaker の学習で RecordIO と Pipe モード が出てきたら、「大規模データをストリーミングで高速に学習」がヒント。データを全部ダウンロードし切る前に学習を始められるのが強みです。

05

間違えやすい！似たものとの違い

「S3 が何でもやってくれる」という思い込みが一番の落とし穴です。役割分担で覚えましょう。

Amazon S3

データをためる場所（オブジェクトストレージ）。それ自体はデータベースではありません。

VS

まわりのサービス

  • クエリ → Athena
  • 変換（ETL） → Glue
  • カタログ（目録） → Glue Data Catalog
🔑 見分け方：S3 は「倉庫」。探す・聞く・変えるは、それぞれ専門のサービスが担当します。

Parquet

列指向形式。Athena / Spark 系の定番で、AWS の分析・学習シーンでまず名前が挙がる形式。

VS

ORC

こちらも列指向形式。Hive 系のエコシステムでよく使われてきた形式。

🔑 見分け方：どちらも列指向。「Parquet ＝ Athena / Spark 系の定番」「ORC ＝ Hive 系」とセットで覚えると見分けやすいです。

S3 Select

S3 の中身を少しだけ絞って取り出すための機能。必要な部分だけ先に絞り込めます。

VS

SQL データベース化？

違います。S3 Select があっても、S3 そのものが SQL データベースになるわけではありません。本格的なクエリは Athena の担当です。

🔑 見分け方：S3 Select は「倉庫の中で少しだけ絞る」機能。SQL で分析したいなら Athena を選びます。
