特徴量を作る道具と、しまう場所
Data Wrangler と Feature Store

Day 6 で学んだ前処理（スケーリングやエンコーディングなど）を、実際にどのツールでどう行うか。今日は「作る」SageMaker Data Wrangler と、「保存して使い回す」SageMaker Feature Store の2つがテーマです。

# Data Wrangler# Feature Store# フィーチャーグループ# ポイントインタイム
💡

一言で言うと

Data Wrangler は特徴量を作る「調理場」、Feature Store は作った特徴量をしまう「冷蔵庫」です。調理の手順を一度決めれば再利用でき、冷蔵庫に入れた特徴量は学習にも推論にも同じものを使えます。

ポイントは、学習と推論でまったく同じ特徴量を使うことです。学習時と推論時で特徴量の作り方がずれると、オフラインでは高精度なのに本番で精度が落ちる「トレーニング／サービングスキュー」が起きます。Feature Store はこのズレを防ぐための仕組みです。

03

比較表で整理する

試験で最も問われるのが「オンラインストアとオフラインストアの使い分け」と、「似た道具同士の違い」です。

Feature Store：オンラインストア vs オフラインストア

同じ特徴量を、用途の違う2つの置き場に保存します。どちらを有効化するかはフィーチャーグループ作成時に選びます。

観点オンラインストアオフラインストア
主な用途 リアルタイム推論での特徴量取得 学習データセットの作成、バッチ推論、探索的分析
保存先 低レイテンシなインメモリ／マネージドストア（最新値向け） Amazon S3（アカウントのバケットに Parquet 形式で保存）
保持するデータ 各レコードの最新値のみ 全履歴（過去の値もすべて残る）
レイテンシ ミリ秒単位の低レイテンシ取得（GetRecord API） Athena で SQL クエリする前提で、秒〜分単位
試験での合言葉 「リアルタイム」「低レイテンシ」「推論時に取得」 「学習データ作成」「履歴」「ポイントインタイム結合」

Data Wrangler vs Glue DataBrew：似た道具の違い

どちらも「画面操作でデータ準備」ができますが、想定するゴールが違います（Day 4 の復習も兼ねて）。

観点SageMaker Data WranglerAWS Glue DataBrew
位置づけ SageMaker Studio 内の、ML 向けデータ準備・特徴量エンジニアリングツール Glue ファミリーの、分析・BI 向け汎用データ準備ツール
分析機能 データインサイト、クイックモデル（特徴量重要度）、ターゲットリーケージ検出など ML 特化の分析 データプロファイル（統計・品質の概要）が中心
書き出し先 Feature Store、SageMaker Pipelines、S3、Jupyter ノートブック（コード） S3、Glue データカタログ経由の分析基盤など
選ぶ場面 この後 SageMaker で学習・推論する前提の前処理 ML に限らない一般的な ETL・データ整形
04

試験で問われるポイント

MLA-C01 では「シナリオ → どの機能で解決するか」の形で問われます。キーワードと機能の対応を押さえましょう。

1

「コードを書かずに前処理」→ Data Wrangler

SageMaker Studio のビジュアル UI で、S3 / Athena / Redshift / Snowflake などからデータを取り込み、300 以上の組み込み変換を画面操作で組み立てます。手順はフロー（.flow）として保存され、そのままジョブ化・再利用できます。

2

フローの書き出し先がそのまま出題範囲

Data Wrangler のフローは、Feature Store への取り込み、SageMaker Pipelines のステップ化、S3 への出力、Jupyter ノートブックへのコード書き出しができます。「前処理をパイプラインに組み込みたい」という要件は Pipelines へのエクスポートが答えになります。

3

「学習と推論で同じ特徴量」→ Feature Store で一元管理

特徴量をフィーチャーグループとして登録し、チームやプロジェクトをまたいで検索・再利用できるのが Feature Store の役割です。学習時と推論時で別々に特徴量を作る構成は、トレーニング／サービングスキューの原因として誤答側に置かれがちです。

4

「未来の情報が混ざるのを防ぐ」→ ポイントインタイム結合

オフラインストアがイベント時刻つきで全履歴を保持しているため、学習データ作成時に「その時点で知り得た値だけ」を結合できます。これにより、予測時点より後の情報が学習に混入するデータリーケージを防げます（Day 6 のリーケージの話の実践編です）。

05

間違えやすい点

選択肢で迷いやすい組み合わせを、「やりがちな誤り」と「正しい選択」の対比で確認します。

❌ リアルタイム推論でオフラインストアを参照

推論のたびに S3 のオフラインストアへ Athena クエリを投げる。履歴検索には向くが、ミリ秒応答が必要な推論ではレイテンシが大きすぎる。

VS

⭕ 推論時はオンラインストアから取得

オンラインストアは最新値を低レイテンシで返す専用設計。GetRecord API で即座に特徴量を取得して推論に使う。

🔑 見分け方：問題文に「リアルタイム」「低レイテンシ」があればオンライン、「学習データ」「履歴」があればオフラインです。

❌ 学習データに「今の最新値」を結合

過去の取引データに、現在の顧客ステータスをそのまま結合する。予測時点では知り得なかった未来の情報が混入し、評価だけが不自然に良くなる。

VS

⭕ ポイントインタイム結合で時点をそろえる

イベント時刻を使って「その取引の時点での値」をオフラインストアから取り出す。学習データが本番の条件と一致し、リーケージを防げる。

🔑 合言葉：学習データは「予測する瞬間に見えていた世界」だけで作ること。これがポイントインタイムの考え方です。

❌ チームごとに特徴量をバラバラに作る

「過去30日の購入金額」をプロジェクトごとに別実装する。定義が微妙にずれ、モデルの再現性も比較可能性も失われる。

VS

⭕ フィーチャーグループに登録して共有

Feature Store に登録すれば、定義は1か所に統一され、誰でも同じ特徴量を検索して再利用できる。

🔑 Feature Store は単なる保存場所ではなく、特徴量の「定義の置き場」です。再利用と一貫性がキーワードになります。
