データ品質の検証と
暗号化・匿名化（PII対応）

悪いデータで学習すれば、悪いモデルができあがります。さらに個人情報を含むデータは、守り方を間違うとそのまま事故のもとに。今日は「品質を検証する」「暗号化する」「PII を見つけて加工する」という、学習前の3つの守りを押さえます。

# データ品質# Glue Data Quality / DQDL# 暗号化（KMS）# PII（Macie / Comprehend）
🛡️

一言で言うと

欠け・重複・型ズレのない良いデータだけを使い、個人情報は暗号化＋匿名化して守ってから学習することです。

01

データが通る「4つの関所」― 検証・暗号化・PII対応・運用監視

ステップをタップすると、その関所でどのサービスが何をするかが切り替わります。データは「入ってくるとき」「保管中」「使う前」「運用中」の各場面で守られます。

› › ›
02

図解：DQDL ルールで「悪いデータ」を止める

Glue Data Quality のルールは DQDL という言語で書きます。左の顧客データに潜む3つの問題を、右のルールがどう検出するか見てみましょう。

例：EC サイトの顧客マスタを取り込む ETL ジョブ。欠損・重複・型ズレのある行が混ざっていたら、学習に使う前に止めたいところです。

INPUT 取り込む顧客データ

customer_idemailage
C001a@example.com34
C001b@example.com28
C003（空）41
C004d@example.com不明

赤いセルが問題箇所：ID の重複、email の欠損、age の型ズレ（数値のはずが文字列）。

DQDL ルールセット

Rules = [
  IsComplete "email",
  IsUnique "customer_id",
  ColumnDataType "age" = "INT"
]
❌ 検証結果：FAIL ― 3つのルールすべてに違反
  • IsComplete：C003 の email が欠けている
  • IsUnique：C001 が2行に重複している
  • ColumnDataType：age に文字列「不明」が混入

ルールに違反したら、ETL ジョブを止める／アラートを出すのが基本動作です。「悪いデータを黙って通す」のではなく、学習データになる前に検出して弾く。これが Glue Data Quality の役割です。ほかにも RowCount（行数）、ColumnCount（列数）、DataFreshness（鮮度）などのルールがあります。

04

試験で問われるポイント

MLA-C01 では「検証のタイミング」「PII の担当分け」「鍵の管理方法」の3点が頻出です。

1

品質チェックは「ETL 時」と「運用中」で担当が違う

データを取り込む段階の検証は Glue Data Quality、モデルが本番で動いている間の入力データの監視は SageMaker Model Monitor です。どちらも「データ品質」に関わりますが、タイミングで使い分けます。「デプロイ後のドリフト監視」と書かれていたら Model Monitor、「ETL ジョブでのルール検証」なら Glue Data Quality が答えです。

2

PII は「発見は Macie」「文章の処理は Comprehend」

S3 バケットのどこに個人情報があるか分からない、という棚卸しは Amazon Macie。レビュー文や問い合わせ文の中の氏名・電話番号を見つけて伏せたい、という文章処理は Amazon Comprehend です。対象が「S3 のファイル」か「テキストの中身」かで切り分けます。

3

暗号化の鍵は KMS が管理する（SSE-S3 との違い）

S3 のサーバー側暗号化には、S3 が鍵を管理する SSE-S3 と、KMS の鍵を使う SSE-KMS があります。SSE-KMS ならキーポリシーで鍵の利用者を制御でき、鍵の使用履歴を CloudTrail で監査できます。SageMaker でも、学習ジョブの出力やボリュームの暗号化に KMS キーを指定するのが定番です。「監査・厳密な鍵管理が必要」と書かれたら SSE-KMS です。

05

間違えやすい！混同しやすいポイント

今日最大の引っかけは「暗号化したから PII 対策は万全」という思い込みと、「匿名化」と「仮名化」の取り違えです。

暗号化

鍵でデータを読み取れない形にする保管の守り。正しい鍵があれば元に戻せる（復号できる）のが前提の仕組み。

VS

匿名化・マスキング

氏名や電話番号そのものを消す・伏せるなど、データの中身を加工して個人を特定できないようにする処理。

🔑 見分け方：暗号化だけでは PII 対策になりません。復号すれば平文に戻るし、学習に使う時点では中身が読める状態です。「守る（暗号化）」と「見えなくする（匿名化・マスキング）」は目的が違うので、両方必要です。

匿名化

個人を特定できる情報を取り除き、元に戻せない（不可逆）形に加工する。本人を再び特定することはできない。

VS

仮名化

氏名を ID などに置き換える加工。対応表（変換テーブル）があれば元の個人に戻せる。対応表自体の管理が重要になる。

🔑 見分け方：キーワードは「戻せるかどうか」。匿名化 ＝ 戻せない、仮名化 ＝ 対応表で戻せる。問題文に「対応表」「再識別できる」とあれば仮名化です。

Amazon Macie

担当は S3 の棚卸し。バケット全体を走査して、個人情報を含むファイルの発見と分類を行う。

VS

Amazon Comprehend

担当は文章の処理。渡されたテキストの中から PII を検出してマスキング（編集）する。

🔑 見分け方：「バケットのどこにあるか分からない」→ Macie、「この文章の中の氏名を伏せたい」→ Comprehend。場所を探すのが Macie、文章を加工するのが Comprehend です。
