# ストリーミング# リアルタイム処理# シャード

一言で言うと

Kinesis は「流れてくるデータ（ストリーム）」を扱うサービスの集まり。自分で処理するなら Data Streams、ためて届けるだけなら Firehose、という使い分けがすべての基本です。

02

図解：シャードとパーティションキー

Data Streams の心臓部です。「どのシャードに入るか」はパーティションキーで決まります。

レコードはパーティションキーのハッシュ値でシャードに振り分けられる

同じパーティションキーを持つレコードは必ず同じシャードに入り、その中では到着した順序が保証されます。シャード1つあたりの処理能力には上限があるため、キーの偏りがそのままボトルネックになります。

送信元アプリkey: user-A
→
Shard 1書込 1MB/秒 or 1,000件/秒過負荷！
送信元アプリkey: user-B
→
Shard 2書込 1MB/秒 or 1,000件/秒
送信元アプリkey: user-C
→
Shard 3書込 1MB/秒 or 1,000件/秒
レコード（データ1件） ホットシャード（集中しすぎ）

⚠️ ホットシャードに注意： 特定ユーザーやデバイスだけが大量にデータを送ると、そのキーを受け持つシャードだけが上限に達してエラー（ProvisionedThroughputExceeded）になります。対策は、パーティションキーを分散させること（例：キーにランダムな接尾辞を付ける）と、シャード数を増やすことです。

4サービスの比較表

🚰

Kinesis Data Streamsストリームの「受け口」

データをリアルタイムに受け取り、自分のプログラムで自由に処理するための基盤。

処理の主体
自分（Lambda、EC2、Flink など読み取り側を自分で用意）
管理すること
シャード数（スループットはシャード数で決まる）
保存期間
既定 24時間、最大 365日 まで延長可（読み直し・再処理ができる）
順序保証
同一 パーティションキー 内でのみ保証
🚚

Amazon Data Firehose旧名：Kinesis Data Firehose

ストリームデータをためて、宛先へ届けることに特化したフルマネージド配信サービス。

処理の主体
AWS（配信はおまかせ。変換したいときだけ Lambda を挟める）
管理すること
ほぼなし。シャード管理不要 で自動スケール
届け先
S3、Redshift、OpenSearch Service など。バッファリングしてまとめて配信
保存期間
保存はしない（バッファは一時的なもの。通過点にすぎない）
📹

Kinesis Video Streams映像・音声専用

カメラやマイクからの映像・音声ストリームを取り込むための専用サービス。

処理の主体
取り込みは AWS、映像の解析は Rekognition Video などと連携
管理すること
デバイス側の SDK で接続するだけ（シャードの概念なし）
保存期間
設定した保持期間のあいだ映像を保存し、後から再生・解析できる
向いている場面
監視カメラの映像解析、ビデオ通話、ドライブレコーダーの取り込み
🔍

Amazon Managed Service for Apache Flink旧名：Kinesis Data Analytics

流れてくるデータに対して、SQL や Flink アプリでリアルタイム分析を行うサービス。

処理の主体
分析クエリは自分で書く。実行基盤は AWS が管理
入力元
Data Streams や Firehose のストリームをそのまま読める
得意なこと
「直近5分間の集計」のような時間ウィンドウ集計、異常検知、フィルタリング
向いている場面
ダッシュボードのリアルタイム更新、ストリームの ETL、即時アラート
04

試験で問われるポイント

MLA-C01 では「どのサービスを選ぶか」の判断軸が問われます。この4つを押さえれば大丈夫です。

1

「自分で処理」か「届けるだけ」か

受け取ったデータを自前のコードでリアルタイム処理したい → Data Streams。S3 などへ保存・配信するだけでよい → Data Firehose。この二分法が最重要の判断軸です。

2

スループット調整 ＝ シャード数の増減

Data Streams の処理能力はシャード数で決まります。「データ量が増えたので処理能力を上げたい」→ シャードを増やす（リシャーディング）。Firehose にはこの概念がなく、自動でスケールします。

3

順序保証は「同一パーティションキー内」だけ

ストリーム全体の順序が保証されるわけではありません。同じキー同士なら順序どおりに読めますが、キー同士の前後関係は保証されません。「順序が大事」な問題ではこの限定が鍵になります。

4

再処理ができるのは Data Streams

Data Streams はデータを保存するので（既定24時間・最大365日）、障害後に同じデータを読み直して再処理できます。Firehose は通過点であり、届けたデータの読み直しはできません。
